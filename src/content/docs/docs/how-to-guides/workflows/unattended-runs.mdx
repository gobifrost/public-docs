---

A workflow that runs manually and a workflow that runs from a schedule or webhook
can behave differently even when the code is identical. The difference can be
the executing identity and the permissions added by the workflow.

## What each trigger runs as

- A form, app, CLI, agent, or API call runs as the calling user.
- A schedule or webhook run has no human caller. It runs in the source's
  organization context under the platform's service identity for that scope.
- Solution ownership supplies the install context; it does not replace the
  trigger’s run identity. A Solution-managed workflow cannot carry a custom run
  identity; `workflows update
  --run-as` refuses with `409 Conflict: Solution-managed entities can only be
  managed by deployment methods`, and the portable workflow manifest has no
  run-identity field.

## Why an integration read can fail

Integration reads resolve the organization's mapping and the integration's
credential. The executing identity must be allowed to read that credential. A
manual run by an operator who can read secrets may succeed while the same
workflow fails unattended with a 401 or an unauthenticated vendor request.

This is not a reason to put credentials in source or in the event payload.
Keep them in configuration/secrets. Review both the run identity and the
workflow’s declared permissions.

<Aside type="caution">
Do not broaden secret-read access across the organization's default identity to
work around one workflow. For a Solution, declare only the permissions that
workflow needs and have a Platform Admin approve them. A dedicated identity is
also an option for a workflow outside a Solution.
</Aside>

## Declare permissions in a Solution

A Solution can request permissions for each workflow without changing which
identity runs it. In that workflow’s existing entry in `.bifrost/workflows.yaml`,
add `requested_permissions`. For example, to request secret-read access:

```yaml
requested_permissions:
  mode: restricted
  grants:
    - permission: secrets.read
```

Declare each additional permission the workflow needs; this example is not a
complete permission list for every integration. These permissions add powers to
the run identity within its existing organization reach. They do not grant
access to additional organizations or attach a custom identity to the Solution.

<Aside type="note">
The approval steps below require a Bifrost release containing
[the Solution permission-request approval fix (#1501)](https://github.com/gobifrost/bifrost/pull/1501).
</Aside>

1. Deploy the Solution with its workflow permission requests.
2. A Platform Admin opens the workflow’s actions, selects **View Settings**, then
   **Access** to inspect the requested permissions and approval status.
3. Select **Review Permission Request**, analyze the selected workflow, and
   review the installed Solution’s requested mode and permissions. Code-analysis
   suggestions are separate from the declaration being approved.
4. Select the workflow, choose **Review selected**, acknowledge the exact
   requested Solution permissions, then choose **Apply reviewed changes**.
5. Reopen **View Settings → Access** and confirm the request is **Approved**.

A new restricted request adds no permissions until approved. An unchanged
request keeps its approval on redeployment; a changed request needs approval
again. Revoked or stale approval adds no permissions. The workflow’s run
identity and organization reach stay unchanged.

Custom run identities remain a separate limitation: Solution-managed workflows
cannot be reassigned with `workflows update --run-as`, and the portable manifest
has no run-identity field. That limitation does not require moving a workflow
outside its Solution just to add approved workflow permissions.

## Other options

- **Run manually while tuning.** A manual run uses the operator’s permissions;
  verify the unattended trigger separately before relying on it.
- **Use a dedicated identity outside a Solution** when the workflow needs a
  different run identity. Create an identity in the appropriate organization,
  grant only the required permissions, and use `workflows update --run-as`.
  This is an alternative for changing identity, not a prerequisite for
  Solution-declared permissions.

## Verify the real execution identity

After configuring a schedule or webhook, run the workflow once from that trigger
and inspect the execution's identity and logs. A successful manual run does not
prove the unattended path can read the same integrations.
